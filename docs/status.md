## Retired performance features (read-only)

AP-029, AP-032, AP-033, AP-035 and AP-036 were derived performance plans. AP-037 phase two (19.19.0, 2026-10-04) retired their plans, scripts and run-start routes. Runs recorded from them stay readable, with reports exactly as rendered before (`specs/037-request-chain-performance` FR-037), but cannot be run again or restored.

**Removal date: 2026-12-31.** On that date the read-only paths are removed:

- the legacy run routes (`GET /runs`, `GET /runs/:runId`, `POST /runs/:runId/cancel`, `GET /runs/:runId/report`) under `/api/test-generation-workflow/performance`, `/api/quick-performance` and `/api/collection-performance`, and `registerLegacyRunRoutes`;
- the frontend "Earlier runs" view (`LegacyRunsView`) and the legacy report golden tests.

The quick test's upload routes (`POST` and `GET /api/quick-performance`) stay: they are a seeding source for request-chain plans. Until the removal date, download any report you want to keep (`?download=true`).

Before removal, `specs/037-request-chain-performance` must settle what happens to the stored legacy run rows (delete, or keep unread) and amend FR-037; that decision is open.

## Current capabilities

The following capabilities are implemented in the current repository:

- OpenAPI 3.x (YAML or JSON) upload, validation, normalization, internal `$ref` resolution, and API-model construction.
- HAR capture and ApiPilot API definition input, both mapped onto the same model with explicit provenance (observed, inferred, declared), credential redaction at extraction, and the same downstream stages (see the [user manual](USER_MANUAL.md#3-1a-uploading-a-har-capture)).
- Explicit operation selection at API review: only the chosen operations, and the schemas they reference, go to deterministic generation and AI enhancement. The full API model is kept for later stages that need unselected operations, such as auth-credential chaining to a token endpoint.
- Deterministic positive, required-field, null/empty, invalid-type, invalid-format, invalid-enum, numeric-boundary, string-boundary, and array-boundary scenarios.
- Specification-grounded response and schema assertions with deterministic per-operation deduplication and provenance.
- Optional AI scenario enhancement through a provider abstraction, with local Transformers.js inference or a deterministic mock provider.
- AI readiness reporting, FIFO serial inference, bounded batching, viability checks, cancellation, incremental progress, and one retry for a malformed batch response.
- Scenario review with accept, reject, edit, regenerate, bulk decisions, validation, rationale, and stale-state handling. The review is locked while it is being finalized, so no decision can land after the approved suite has been projected.
- Deterministic and optional AI-assisted API dependency analysis with evidence, confidence classes, graph construction, and ordered workflow candidates.
- Workflow review and workflow-aware Postman rendering.
- Postman collection, environment, and artifact README generation from approved test intent.
- OpenAPI parameter serialization for supported `style` and `explode` combinations, credential variables per distinct security scheme, resource-qualified path-parameter variables (`/users/{id}` → `{{user_id}}`), automatic producer-to-consumer chaining, and OAuth2 client-credentials token setup.
- Explicit Newman execution, one request at a time, with cancellation, safety confirmation, request delays, and categorized pass/fail/not-attempted outcomes. In the UI, a generated collection runs through "Import & Run Collection" after the guided workflow hands it off; the guided workflow's own execution endpoints remain available over HTTP, where a request whose data prerequisite failed is held back as "dependency not met" and every result records its processing stage.
- On-demand AI failure analysis of one failed request in an Import & Run Collection run (_implementation complete, AI evaluation pending_; see [Limitations](#limitations)). Deterministic rules decide the likely cause (specification mismatch, environment issue, or downstream-service issue) or "insufficient evidence", with a fixed High or Moderate strength and the rule that decided it. The local AI adds only a plain-language summary and suggested next steps, labelled as an inference. The redacted evidence behind the cause is shown, and if the AI is unavailable the cause and evidence are still shown and stored. When the failed request came from the session's current guided workflow, its operation, scenario, documented responses, and upstream workflow steps are attached as specification context. Analyses are stored with the run and never send a request to the target API.
- k6 performance testing from the guided workflow (AP-029), a quick test from a specification (AP-032), a collection (AP-036), step edits (AP-033) and user-defined journeys (AP-035) were derived plans; AP-037 phase two (19.19.0) retired them. Those entry points now create request-chain plans (below), and runs recorded from the derived plans stay readable, with their reports unchanged, but cannot be run again or restored.
- Run k6 Script (`specs/034-run-user-k6-script`, _implementation complete, manual browser walkthrough pending_): upload or write a k6 script, which ApiPilot checks before storing (allowlisted k6 built-ins only, no file access, no code built from text, no `handleSummary`). Confirm its exact content (bound to its SHA-256), map the names it reads to environment values, optionally replace its load with a profile, and run it with your own k6 on an explicit trigger, with a self-contained report grouped by k6 request name. Scripts, runs and results are stored encrypted. A script downloaded from any performance plan can be run here as your own.
- Performance plans: request chains (`specs/037-request-chain-performance`, _implementation complete; phase one walkthrough done, phase two browser walkthrough pending_): a performance plan you own and edit freely, as in Postman or JMeter. It holds chains of concrete steps, each with its own method, URL, query, headers, body, expected statuses, extractors, checks, run frequency (every iteration, once per virtual user, once before load) and think time. A plan can start empty or be seeded once from the quick test's specification, the guided workflow's Performance Testing stage or selected collection requests, and is never re-derived from its source; each entry point lists the plans created from it. A shared plan check blocks the script while a value is used before it is extracted. Credentials typed as text move into a secret environment value. CSV data sets supply per-iteration or per-virtual-user rows. Plans and data sets are stored encrypted, and a run's report shows each chain, step, check and data set.
- Security Lab (`specs/057-security-lab-v1`): deterministic specification security analysis with effective-security resolution and classified observations that never claim a vulnerability; deterministic, schema-validated security scenarios across eight supported categories; version-bound review and approval with batch review; target profiles with write-only credentials and a destination policy enforced at connect time; a confirmed, bounded, cancellable run against a `local`, `dev`, `qa` or `staging` target; deterministic evaluation, confidence and one finding per scenario version with occurrences; an Overview, an HTML or JSON report, a Postman export of approved scenarios; retained work that outlives the session; and optional locally generated scenario suggestions kept as drafts. See the [user manual](USER_MANUAL.md#6c-security-lab).
- Per-browser session isolation using an unguessable HTTP-only cookie and a 60-minute idle eviction policy.
- Local SQLite persistence for environments, encrypted credential-like values, execution history, and AI readiness/benchmark diagnostics.
- Standalone import and execution of an externally-authored Postman collection and environment pair — no OpenAPI specification or guided workflow required — with the same per-request pass/fail reporting, a mandatory unverified-content confirmation before its first run, and full pre-request/test-script fidelity via Newman's own sandbox.
- A Postman-style collection and variable editor for an uploaded collection: a navigable folder/request tree, a resolved-vs-raw request preview, a variable panel showing each variable's value/source/resolved-or-missing status, full method/URL/header/body/test-script editing, add/delete/rename/reorder and move between folders for requests and folders (a move carries the item's inherited auth and the scripts of the folders it leaves), and a selective-run checklist that can also reorder requests within their folder, each row showing the request's folder, method, name and endpoint path. Each request shows its effective auth and where it comes from, and every variable it uses with its set/missing status; secret literals in auth fields are never sent to the browser. Headers that a request's `bearer` or header-located `apikey` auth adds at run time are shown as display-only "from auth" entries, with their `{{variables}}` highlighted and where the auth comes from. Edits are saved into ApiPilot's stored copy of the uploaded collection, with each edited request marked so that run results flag it as edited; the uploaded file itself, and any generated scenarios and provenance behind a handed-off collection, are never modified. The editor is read-only while a run of that collection is in progress. Unresolved variables are marked missing but do not block a run, and values that test scripts capture during a run (`pm.environment.set`) are saved back so the preview and the next run use them. A generated collection reaches this editor through the hand-off, as an uploaded collection (see [Limitations](#limitations)).
- A shared frontend design system and application shell: design tokens for light/dark mode (a manual toggle persisted per browser, defaulting to the OS preference), a reusable component library (buttons, status/decision badges, HTTP method indicators, AI-vs-deterministic provenance indicators, tabs, dialogs, empty/error/loading states), and a workflow stage tracker that explains why a locked stage is unavailable — used consistently across every page.
- React/Vite frontend with accessible review controls, progress reporting, filtering, bulk actions, loading/error/empty states, and frontend error forwarding to the backend logger.

## Limitations

Current intentional limitations include:

- The guided workflow's input is one file: OpenAPI 3.x (YAML or JSON), a HAR capture, or an ApiPilot API definition. Swagger 2.0 and external reference retrieval are unsupported there. A HAR is evidence of one session, not a contract: its tests assert only observed statuses, its negatives need three observations, and compressed bodies and multipart file parts are not used. An externally-authored Postman collection may instead be imported and executed directly through the separate standalone entry point (with its own mandatory unverified-content confirmation) — this is a deliberate, narrowly-scoped exception, not a general uploaded-content execution capability.
- Supported parameter serialization is explicit; unsupported styles such as content-based, matrix, and label forms are reported rather than guessed where the implementation cannot safely render them.
- Local AI performance depends heavily on the selected model and machine. Large specifications may settle as partial or not completed at the configured run budget while retaining successful units.
- Workflow generation state is not durable across backend restarts, even though environments and execution history are persisted.
- There is no user authentication, multi-user account model, external database, external queue, scheduled execution, or cloud AI provider.
- AP-031 (formerly AP-018), AI failure analysis (`specs/030-ai-failure-analysis`), explains one failed request in an Import & Run Collection run: fixed rules decide the likely cause from the recorded evidence, and the local AI adds a labelled summary and next steps, plus specification context when the collection came from the current guided workflow. Its status is _implementation complete, AI evaluation pending_. On the 12-case synthetic evaluation corpus the rules match every label, and the former default `Qwen2.5-0.5B-Instruct` wrote a usable explanation for all 12 with no contradictions (`specs/030-ai-failure-analysis/evaluation.md`, run 5), and the current default `Qwen3-1.7B-ONNX` for 11 of 12 with no contradictions, at a 34 s median (run 6). It is not recorded as Implemented until the corpus also contains at least 4 real, redacted recorded failures. The cause is a likely cause, not a confirmed root cause; a failure no rule covers is reported as "insufficient evidence". It does not analyze runs made through the guided workflow's API-only execution endpoints. Some AI enhancement and manual Postman acceptance work remains follow-up validation rather than a missing runtime pipeline.
- The Postman-style collection/variable editor (AP-028) operates on uploaded collections. A generated collection reaches it by being handed off and uploaded, at which point it is stored and confirmed like any externally-authored collection (`specs/028` Clarifications 2026-09-23). The guided workflow's own execution endpoints are an API-only path with no editing surface.
- Dependency-aware holding of requests (`specs/029-execution-gap-closure`) applies to the guided workflow's API-only execution path. Uploaded-collection runs execute every selected request in collection order, and a request that depends on a failed one records its own outcome.
- AP-029 (k6 performance testing), AP-032 (the quick performance test), AP-033 (step edits), AP-035 (user-defined journeys) and AP-036 (a performance test from a collection) were derived plans; AP-037 phase two (19.19.0) retired them. Their runs can be opened, with the report as it was rendered, but not run again or restored. Runs apply no limit on virtual users or duration, include write steps as the plan has them, and never clean up what they create.
- AP-037, request-chain performance plans (`specs/037-request-chain-performance`), is _implementation complete_: `npm run test:k6-real -w backend` passed against k6 v2.3.0 on Windows, and a scripted browser walkthrough of quickstart scenarios 1 to 9 passed (2026-10-03). Phase two (19.19.0) retired the derived plans; its scripted browser walkthrough (quickstart scenario 10) passed on 2026-10-04 (19.19.1) and awaits acceptance. Creating a plan from a collection converts only a fixed set of script statements and runs no script; the rest is listed in the seeding report. A downloaded script that reads a data set cannot be run in Run k6 Script, which never lets a script open files. Extractors read JSON body fields and response headers only.
- AP-034, Run k6 Script (`specs/034-run-user-k6-script`), is _implementation complete, manual browser walkthrough pending_; `npm run test:k6-real -w backend` passed against k6 v2.3.0 on Windows (2026-10-01). ApiPilot checks a supplied script statically and runs only the bytes you confirmed, but it cannot restrict which hosts the script contacts, and what the script does is your responsibility. The check accepts a strict JavaScript subset: reading a property by a key built at run time is refused (use a `Map`), test data files cannot be read, and WebSocket, gRPC and browser tests are not supported.

- Security Lab (AP-057) is a bounded set of checks, not a penetration test. Sensitive business flows and SSRF are limited (an observation and a limitation, no executable scenario), API inventory is analysis only, OAuth2 token flows are unsupported, and production targets are refused. A specification analysis cannot prove a vulnerability and an assessment with no findings is not proof of security. Retained work is reachable only from the browser whose `apipilotOwner` cookie created it. The owner cookie was checked only in Chromium on Windows (it survives browser and backend restarts, and a fresh context sees none of the retained work); Firefox, Edge and a true private window were not checked (spike T004). The optional AI suggestion has no evaluation corpus, so its quality is unmeasured, and with the default local model (Qwen3-1.7B on CPU) a request covering many operations can exceed the 270 second inference timeout and be reported as the model being unavailable. Generation can be widened to all operations or limited by category, but cannot yet be narrowed to hand-picked operations from the UI (the API accepts a custom scope).

The implementation status of every feature is maintained in [specs/ROADMAP.md](../specs/ROADMAP.md); that roadmap identifies implemented features and remaining validation tasks. Feature `spec.md` files provide the normative behavior and contracts.

## Known dependency advisories

As of 2026-10-12, `npm audit` reports 7 remaining findings (6 high, 1 moderate), including dependent packages, from three unresolved advisories:

- [Faker code execution](https://github.com/advisories/GHSA-qxc2-j82w-r537): Postman Collection still requires Faker 5's legacy API; the patched Faker 10.5+ API is not a drop-in replacement.
- [CSV prototype replacement](https://github.com/advisories/GHSA-8cw4-87c7-c6xx): Newman 6 expects the callable `csv-parse` 4 export; patched version 7.0.2+ exposes a named `parse` function instead.
- [Forge RSA signature verification](https://github.com/advisories/GHSA-86w9-cpqp-85rv): the latest release, `node-forge@1.4.0`, is still affected and no patched release is published.

These findings are not suppressed. Do not run `npm audit fix --force` as a routine fix: its suggested Newman/Postman downgrades change execution contracts. Full remediation needs compatible upstream fixes or an explicitly reviewed migration.
