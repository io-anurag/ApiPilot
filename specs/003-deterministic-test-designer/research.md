# Phase 0 Research: Deterministic Test Designer

## Decision: Extend `SchemaConstraint` and `buildApiModel` to capture `minLength`/`maxLength`/`minItems`/`maxItems`

**Rationale**: The AP-002 `ApiModel.SchemaConstraint` type currently extracts `type`,
`required`, `properties`, `items`, `enum`, `format`, `minimum`, `maximum`, and `pattern`,
but not `minLength`/`maxLength` (string) or `minItems`/`maxItems` (array). FR-006/FR-007 of
this feature require string- and array-boundary scenarios, which are impossible to
generate deterministically without these declared constraints. Extending the existing
domain type additively (new optional fields) is preferred over re-parsing the raw OpenAPI
document inside `testDesign/` — that would duplicate extraction logic already owned by
`openapi/buildApiModel.ts` and violate constitution IX (Separation of Concerns) and X
(Domain Model First: `ApiModel` is the single source of extracted schema facts).

**Alternatives considered**: Having `testDesign/` re-read raw schema nodes independently
was rejected — it would create a second, divergent path for extracting the same
specification facts already owned by the OpenAPI Specification Engine, risking drift
between what `ApiModel` reports and what the Test Designer actually uses.

## Decision: New stateless endpoint `POST /api/test-models`

**Rationale**: Consistent with AP-002's "no persistence" decision, the backend does not
retain an uploaded specification or its `ApiModel` beyond a single request/response. The
Deterministic Test Designer therefore exposes a new endpoint that accepts a full `ApiModel`
(the same JSON shape already returned by `POST /api/specifications`) in the request body
and returns the generated `TestModel`. The frontend passes the `apiModel` it already
received from the upload/analysis step back to this endpoint — no new storage is
introduced, and the two features remain independently testable (constitution IX, XVII, XXI).

**Alternatives considered**: Persisting the `ApiModel` server-side keyed by a session/spec
ID (so the client could just send an ID) was rejected — it would introduce state and
storage infrastructure purely to save re-sending a JSON payload, which constitution XXVII
(Prefer Simple Architecture) disallows without a proven need.

## Decision: Deterministic synthetic value generation, keyed by declared type/format

**Rationale**: Each rule module needs concrete values to build a request (e.g., "a string
where an integer is expected," "a value below `minLength`"). Values are generated by a
small, pure `valueGenerators.ts` module using fixed, documented conventions per declared
`type`/`format`/`pattern` (e.g., `invalid-type` for a `string` field with the intended value
being the wrong type: an object `{}` for `type: "string"`, JSON-safe but incompatible; for
`format: "email"` violation: a plain string containing no `@`; for `format: "date-time"`
violation: a non-ISO-8601 string; for `format: "uuid"` violation: a string that is not a
valid UUID; for `pattern`: any fixed literal string that does not match the pattern, e.g.
prefixing/mutating a documented example if present, or a conservative fallback literal).
This keeps generation deterministic and reproducible (constitution XXIV) without adding a
fuzzing/property-based-testing dependency (constitution XXVII).

**Alternatives considered**: Using a third-party fake-data/fuzzing library (e.g., for
random-but-type-correct or type-incorrect values) was rejected — randomness would make
generated scenarios non-reproducible across runs (violating constitution XVI/XXIV) and adds
a dependency for a problem solvable with small, deterministic, testable helper functions.

## Decision: Recursive nested-field traversal for required-field/invalid-type/invalid-format scenarios

**Rationale**: Per the spec's Clarifications, required-field and type/format scenarios
must cover fields nested at any depth inside object-typed request body properties. The
generator walks `SchemaConstraint.properties` recursively from the request body root,
building a dotted field path (e.g., `address.zipCode`) for each field. For each required
field encountered (at any depth), the rule mutates a deep clone of a synthesized
"positive" request body at that exact path (delete the key for missing-field, set `null`
for null-value, set `""`/`[]`/`{}` for empty-value depending on the field's declared type)
rather than flattening the object, preserving the surrounding valid structure exactly as a
real client would send it.

**Alternatives considered**: Limiting traversal to one level (top-level object properties
only) was rejected per the resolved clarification and because it would silently under-test
common request shapes that nest required fields inside sub-objects (e.g.,
`{ "address": { "zipCode": "..." } }`).

## Decision: Location-appropriate scenario set for parameters (path vs. query/header)

**Rationale**: Per the spec's Clarifications, required path parameters do not receive
missing/null/empty-value scenarios (a missing path segment is a routing/404 concern
handled by the HTTP layer, not a payload-validation concern the `TestModel` should assert
on) but do receive invalid-type, invalid-enum, invalid-format, and boundary scenarios.
Required query/header parameters receive the full set, matching request body fields,
since omitting a query/header parameter is a legitimate, observable request the API must
validate.

**Alternatives considered**: Full parity across all parameter locations was rejected per
the resolved clarification — it would generate a "missing path parameter" scenario whose
only realistic effect is a routing mismatch, not a meaningful API-level assertion.

## Decision: Deterministic response-assertion selection, with explicit gaps when no basis exists

**Rationale**: For a **positive** scenario, the expected assertion is the documented
response with the lowest 2xx status code (ascending numeric order, e.g., `200` before
`201`); if no 2xx response is documented, the single lowest documented status code overall
is used (documented non-2xx-only operations still get a scenario per FR-001, with an
assertion reflecting what is actually documented, never an assumed `200` — satisfying the
spec's edge case). For a **negative** scenario (missing/null/empty/invalid-type/
invalid-format/invalid-enum/boundary), the expected assertion is the documented response
with the lowest 4xx status code; if the operation documents no 4xx (or no error) response
at all, the scenario is still generated (it still carries a valid, executable request) but
its `assertions` array is left empty and its `Provenance.description` explicitly records
"no documented error response available for this operation" — surfacing the gap rather
than fabricating a `400` that the specification never promised (constitution I, XIV, XIX).

**Alternatives considered**: Always defaulting negative scenarios to `400` was rejected —
it would silently invent contract information the specification never declared, directly
violating constitution I (Specification Is the Source of Truth) and XIV (No Silent
Assumptions).

## Decision: Per-operation deduplication key

**Rationale**: Two scenarios are considered duplicates within the same operation when a
canonical JSON serialization of `{ method, path, request, assertions }` is identical
(object keys sorted deterministically before serialization, so key order never causes a
false mismatch). When a duplicate is found, the first-generated scenario is retained and
the duplicate rule's identifier is appended to the retained scenario's
`Provenance.duplicateOfRules` list, so the merged scenario remains traceable to every rule
that would have produced it (FR-012, spec.md User Story 3 Acceptance Scenario 2).

**Alternatives considered**: Comparing only the generated request (ignoring assertions) was
rejected — two scenarios with the same request but different expected assertions (which
should not normally happen given deterministic assertion selection, but is not provably
impossible for edge-case schemas) are not truly equivalent tests and must not be silently
collapsed.

## Decision: Scenario IDs via `crypto.randomUUID()`

**Rationale**: Each `TestScenario` needs a stable-enough identifier for UI list rendering
and future review-state tracking (AP-006). Node.js 20's built-in `crypto.randomUUID()`
requires no new dependency (constitution XXVII) and is sufficient since scenario *content*
(request/assertions/provenance), not the ID, is what determines equivalence for
deduplication and reproducibility.

**Alternatives considered**: Deriving IDs deterministically from scenario content (e.g., a
content hash) was considered but rejected as unnecessary — no requirement calls for
identical IDs across repeated generations, and it would add complexity for no proven
benefit.
