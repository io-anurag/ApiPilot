# Feature Specification: AI Failure Analysis

**Feature Branch**: `[030-ai-failure-analysis]`

**Created**: 2026-09-23

**Status**: Draft

**Input**: User description: "AP-018 — AI Failure Analysis" (renumbered to AP-031 on 2026-09-23)

**Product identifier**: `AP-031` (post-MVP, per `specs/ROADMAP.md`). This feature was listed as
`AP-018` until 2026-09-23. It was renumbered to AP-031 because AP-030 was already taken by Test
Execution Gap Closure (`specs/029-execution-gap-closure`). AP-018 is retired. This spec directory
is numbered `030` per the repository's sequential feature-directory convention. The directory
number and the `AP-###` product identifier are independent, as with
`specs/017-session-workflow-isolation` and `specs/018-test-execution-results`. `AP-031` is the
canonical identifier used in cross-references, commit messages, and `specs/ROADMAP.md`.

**Relationship to prerequisite specifications**: This feature analyzes failed requests in
uploaded-collection execution runs produced by AP-026 (External Postman Collection Import &
Execution, `specs/026-external-collection-execution`). Since 2026-09-23 that is the only path the
UI uses to run a collection, including one generated by the guided workflow (specs/009 hand-off).
When a failed request was generated by the session's current guided workflow, the analysis also
uses that workflow's specification context: the scenario, the operation from the `ApiModel`, and
AP-008's dependency and integration-workflow data. Inference goes only through AP-004's existing
`AIProvider` abstraction (local or mock). Analyses are stored in AP-025's local persistence layer
(`specs/025-local-persistence-layer`), which this feature extends with one new record kind.

This feature makes three additive changes to existing contracts:
- AP-026's per-request result records the executed request's identity (FR-017).
- AP-004's inference request accepts an optional feature-supplied system instruction (see
  `plan.md`).
- AP-004's provider can report when it actually starts working on a request, so waiting and
  generating can be shown separately (FR-016, SC-005; see `plan.md`).

It does not change how AP-026 executes, or how AP-008 or AP-004 behave for their existing callers.
AP-017's run endpoints (`specs/018-test-execution-results`), which are now API-only, are out of
scope (Clarifications 2026-09-23).

## Clarifications

### Session 2026-09-23

- Q: When should AI failure analysis run? → A: On demand, per failed request, only when the user
  explicitly asks. Never automatically when a run completes (FR-012).
- Q: Should a generated analysis survive a backend restart? → A: Yes. It is persisted alongside
  its run in the AP-025 local persistence layer and shares that run's session-scoped lifetime
  (FR-013).
- Q: Which runs' failures can be analyzed? → A: Any failed request in any run still in the
  session's persisted run history (FR-014).
- Q: The UI only produces AP-026 uploaded-collection runs, whose results carry no link to a
  scenario, operation or workflow, while AP-017 runs are reachable only through the API. Which
  results should be analyzed? → A: AP-026 uploaded-collection runs. Each stored result records
  the executed request's identity. When the session's current guided workflow generated that
  request, the analysis attaches its operation, scenario and dependency context. Otherwise the
  analysis states that specification context is unavailable. AP-017 runs are out of scope for this
  feature (FR-001, FR-004, FR-017, FR-018). Found during `/speckit-plan`.
- Q: When one failure analysis is already running in a session, what should happen if the user
  asks to analyze a different failed request? → A: Only one analysis runs at a time per session.
  While it runs, other "Analyze" actions are unavailable and the system rejects further requests
  with an explicit reason. The time limit counts from when the model starts working. Any wait
  behind other AI work is shown as "waiting for the local AI" (FR-016, SC-005).
- Q: Can a user analyze a failed request while its run is still executing other requests? → A:
  Yes. Any failed result already recorded can be analyzed while the run continues (FR-001).
- Q: How should the analysis show its confidence to the user? → A: As a plain label, "Moderate"
  (0.5 to below 0.75) or "High" (0.75 and above), with the exact value next to it in smaller text,
  for example "Moderate (0.62)" (FR-003).
- Q: Should the analysis show only the evidence the AI cited, or also the rest of the evidence it
  was given? → A: Cited evidence is shown by default. The rest is shown in a collapsed "Other
  evidence considered" section (FR-003).

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Understand why a request failed (Priority: P1)

A QA engineer reviewing an execution run sees a failed request and wants to understand, in plain
language, why it most likely failed. They should not have to cross-reference the raw
request/response, the collection's tests and the OpenAPI specification by hand.

**Why this priority**: This is the feature's reason for existing: turning a raw pass/fail result
into an explained, actionable one.

**Independent Test**: Request analysis for one failed request in an uploaded-collection run and
verify that the explanation, evidence and confidence are all derived from that request's own
recorded data. This works for a collection ApiPilot did not generate.

**Acceptance Scenarios**:

1. **Given** a run, completed or still in progress, containing a recorded failed request with a
   failure category and test outcomes, **When** the user requests failure analysis for that request, **Then** the system
   returns a plain-language summary, a likely-cause classification, a confidence level, and
   supporting evidence drawn from that request's own status code, failure category and test
   outcomes.
2. **Given** a failed request whose run targeted a `"local"` tier and therefore has a recorded raw
   request/response capture, **When** the user requests failure analysis, **Then** the redacted
   raw request/response detail is used as additional evidence.
3. **Given** a failed request whose run targeted a non-local tier (no raw capture), **When** the
   user requests failure analysis, **Then** the analysis still completes using only the evidence
   available (status code, failure category, test outcomes) and does not claim access to data it
   does not have.
4. **Given** a request whose outcome is `"passed"` or `"not-attempted"`, **When** the user
   requests failure analysis for it, **Then** the system explicitly rejects the request rather
   than fabricating a failure explanation.

---

### User Story 2 - See specification and dependency context for a failure (Priority: P2)

A QA engineer runs a collection generated by the guided workflow and investigates a failure. They
want to see which operation and scenario the request came from, and, for a workflow step, whether
an earlier step that supplied one of its values also failed in the same run.

**Why this priority**: It changes where the engineer looks next (this operation or an upstream
one), but the single-request explanation from User Story 1 is useful without it.

**Independent Test**: Run a generated collection containing an integration workflow in which the
first step fails and the second step then fails. Request analysis for the second step and verify
that it names its operation and scenario and identifies the failed first step as upstream
context. Separately, analyze a failed request from a collection ApiPilot did not generate and
verify that the analysis says specification context is unavailable and invents none.

**Acceptance Scenarios**:

1. **Given** a failed request generated by the session's current guided workflow, **When** the
   user requests failure analysis, **Then** the analysis names the originating operation (path and
   method) and scenario.
2. **Given** a failed request that is a step in an approved integration workflow and consumes a
   value produced by an earlier step, **When** the user requests failure analysis, **Then** the
   analysis names that upstream step and reports that step's own outcome in the same run (passed,
   failed, or not present in the run).
3. **Given** a failed request that cannot be matched to the session's current guided workflow
   (the collection was not generated by it, a different workflow has since started, or the
   workflow is gone after a backend restart), **When** the user requests failure analysis,
   **Then** the analysis states that specification context is unavailable and why, and contains
   no operation, scenario or dependency claims.
4. **Given** a matched request that was edited in the collection editor after generation, **When**
   the user requests failure analysis, **Then** the analysis notes that the executed request
   differs from the generated one.

---

### User Story 3 - Be told plainly when the AI cannot confidently explain a failure (Priority: P3)

A QA engineer requests analysis for a failure with little distinguishing evidence. They need to be
told that the AI could not determine a likely cause, rather than receive a confident-sounding
guess.

**Why this priority**: It protects trust in the other two stories. Without it, users cannot tell a
well-evidenced explanation from a fabricated one.

**Independent Test**: Request analysis where the model reports confidence below the planned
threshold, or cites no valid evidence, and verify that the result is an explicit "insufficient
evidence" outcome, never a specific cause.

**Acceptance Scenarios**:

1. **Given** a failed request whose available evidence cannot support a specific likely cause,
   **When** the user requests failure analysis, **Then** the system returns an explicit
   "insufficient evidence" outcome rather than a low-quality guess presented as a normal result.
2. **Given** the AI provider is unavailable or returns an error, **When** the user requests
   failure analysis, **Then** the system returns a structured, categorized error (matching the
   existing `AIErrorCategory` conventions) rather than nothing or a fabricated analysis.

---

### Edge Cases

- The configured `AIProvider` is not ready when analysis is requested. The request fails with a
  structured, categorized error, never a silent empty result.
- A failed request has no test outcomes and no response (for example a connectivity failure on a
  non-local tier). The analysis works from the little evidence there is, and this may lead to an
  "insufficient evidence" outcome (User Story 3).
- The referenced run or result no longer exists, for example because its session was
  idle-evicted. The request fails with an explicit not-found error.
- The result was stored before this feature existed and has no recorded request identity. It is
  still eligible for analysis, but specification context is reported as unavailable for that
  reason.
- The user requests analysis for the same failed request more than once. The new analysis
  replaces the stored one as a single unit (FR-015), and a failed re-request leaves the earlier
  stored analysis in place.
- The user requests analysis while another analysis in the same session is still generating,
  whether for the same request or a different one. The new request is rejected with an explicit
  reason (FR-016).
- The local AI is still busy with earlier AI work, such as another session's request or a running
  AI scenario enhancement, when an analysis starts. The UI shows "waiting for the local AI" until
  the model starts on this analysis, and the time limit applies from that point (SC-005).
- The backend restarts. Stored analyses are still shown for their runs (FR-013), including the
  specification context captured when they were generated, even though the in-memory guided
  workflow is gone. An analysis that was mid-generation is not stored, and the user can request it
  again.
- The failed request belongs to a `"cancelled"` run, or to a run whose collection has since been
  removed. Analysis remains available for its failed requests. Its `"not-attempted"` requests
  remain ineligible.
- The request is the synthesized OAuth2 token-fetch request (AP-024), which has no originating
  scenario. It is analyzed without specification context, and the reason is stated.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: System MUST let a user request an AI-generated failure analysis for a single
  request result, in an AP-026 uploaded-collection run, whose outcome is `"failed"`. This applies
  to any recorded result, whatever the run's status: in progress, completed or cancelled. A
  recorded result never changes afterwards.
- **FR-002**: System MUST reject an analysis request for a result whose outcome is `"passed"` or
  `"not-attempted"`, with an explicit, typed reason distinct from an AI provider error.
- **FR-003**: Each failure analysis MUST include:
  - a plain-language failure summary;
  - a likely-cause classification: "potential specification mismatch", "potential environment
    issue", "potential downstream-service issue", or an explicit "insufficient evidence" outcome;
  - the affected request (method and name, plus the operation path when specification context is
    matched);
  - a confidence level, shown as "Moderate" (0.5 to below 0.75) or "High" (0.75 and above)
    together with the exact value, for example "Moderate (0.62)". An "insufficient evidence"
    outcome shows no cause confidence label;
  - supporting evidence drawn only from that request's own recorded data (status code, failure
    category, test outcomes, and the redacted raw capture when present) and from matched
    specification context. The evidence the AI cited is shown by default. The rest of the evidence
    it was given is shown in a collapsed "Other evidence considered" section;
  - suggested next investigation steps.
- **FR-004**: When a failed request is matched to the session's current guided workflow (FR-018)
  and participates in an approved integration workflow or a recorded dependency relationship, the
  analysis MUST include that context: the upstream operation that supplies a consumed value, and
  that upstream request's outcome in the same run when it is present. It MUST NOT fabricate such
  context when no match or relationship exists.
- **FR-005**: System MUST perform every AI inference for failure analysis through the existing
  `AIProvider` abstraction only (local or mock provider). It MUST NOT call a model or library
  directly, and MUST NOT use a cloud provider.
- **FR-006**: When the `AIProvider` is not ready, or inference fails or cannot fit its time budget,
  the system MUST return a structured, categorized error consistent with the existing AI-assisted
  features, rather than omitting the analysis or fabricating one.
- **FR-007**: Every AI-produced explanation MUST be visibly labeled as an inference, never
  presented as a confirmed root cause.
- **FR-008**: When the AI's reported confidence is below the threshold defined in `plan.md`, or the
  answer cites no valid evidence, the system MUST return an explicit "insufficient evidence"
  outcome rather than a specific cause.
- **FR-009**: Failure analysis MUST NOT execute any API request, modify test execution, or alter
  any run or result record other than the additive request identity recorded at execution time
  (FR-017).
- **FR-010**: Every failure analysis MUST record its provenance: the run and result it was
  generated from, the model and provider identity, the prompt/response version, and a generation
  timestamp. This keeps it distinguishable from specification-derived, rule-derived and
  user-defined information.
- **FR-011**: Failure analysis input and output MUST NOT include any credential value, secret, or
  raw environment variable value, whether sourced from the raw capture or elsewhere.
- **FR-012**: System MUST generate a failure analysis only when a user explicitly requests it for
  one specific failed request. It MUST NOT analyze failures automatically when a run completes, in
  the background, or by hidden retry.
- **FR-013**: A generated failure analysis MUST be durably persisted alongside its run in the
  existing local persistence layer (AP-025), so it survives a backend restart. It shares that
  run's session-scoped lifetime and is removed when the owning session is idle-evicted.
- **FR-014**: A user MUST be able to request failure analysis for a failed request in any run
  still present in the session's persisted run history, not only the most recent run.
- **FR-015**: Requesting analysis again for a request that already has a stored analysis MUST
  replace it as one complete unit. Earlier attempts are not kept, and a reader MUST never observe
  a mix of the old and new analysis. When the new attempt fails, the stored analysis MUST remain
  unchanged.
- **FR-016**: At most one failure analysis MUST be generating per session at any time. While one
  is generating, the system MUST reject any further analysis request in that session, whether for
  the same request or a different one, with an explicit, typed reason, rather than queueing it.
  The UI MUST make the "Analyze" action unavailable for every result while an analysis is
  generating, and MUST say which request is being analyzed.
- **FR-017**: Every uploaded-collection request result recorded from now on MUST carry the
  executed request's own identity from the collection. Results recorded before this change stay
  valid without it.
- **FR-018**: Specification context MUST be attached only by exact identity match: the executed
  request's identity equals a request in the session's current guided-workflow collection. It MUST
  NOT be attached by name or path similarity. When there is no match, the analysis MUST state why
  (no identity recorded, no generated collection in the session, not generated by the current
  workflow, or no originating scenario). The context used MUST be stored with the analysis so it
  remains readable after the workflow is gone.

### Key Entities *(include if feature involves data)*

- **FailureAnalysis**: The AI-generated explanation for one failed uploaded-collection request
  result. It carries:
  - the run and result position it explains;
  - a conclusion: a likely cause with confidence, or insufficient evidence;
  - a plain-language summary, the evidence items it cites, and suggested investigation steps;
  - the specification context used, or the reason it was unavailable;
  - provenance.

  At most one stored analysis exists per failed request, and it has the same lifetime as its run.
- **FailureEvidence**: One deterministic, redacted fact extracted from the result or its matched
  context (for example "response status 500" or "test 'Status code is 201' failed"). The AI can
  cite evidence but cannot create it.
- **SpecificationContext**: The matched operation, scenario, and upstream workflow steps with
  their outcomes in the same run, captured at analysis time.
- **UploadedRequestResult** *(existing, AP-026)*: The input record. It gains one optional field,
  the executed request's identity (FR-017), and is otherwise unchanged.
- **ApiModel, TestModel, IntegrationWorkflow, ApiDependencyGraph** *(existing)*: Read, when
  matched, from the session's current guided workflow. Unchanged by this feature.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: A QA engineer investigating a failed request receives a plain-language likely-cause
  explanation with cited supporting evidence, without reading raw logs or cross-referencing the
  specification by hand.
- **SC-002**: 100% of analysis requests for an eligible failed request resolve to a specific
  likely cause with a confidence level, an explicit "insufficient evidence" outcome, or a
  structured error. None is blank or silently dropped.
- **SC-003**: No failure analysis, prompt or log entry contains a credential value, secret or raw
  environment variable value. This is verified by tests over inputs with and without a raw
  capture.
- **SC-004**: When a failed request matches the current workflow and has upstream context, 100% of
  its analyses show that context. When it does not match, 0% contain operation, scenario or
  dependency claims.
- **SC-005**: Once the local model starts on an analysis, the request resolves (analysis,
  insufficient evidence, or structured error) within the per-inference timeout already configured
  for local AI. The user can always tell from the UI whether the analysis is waiting for the local
  AI or is being generated.

## Assumptions

- The feature reuses the configured local or mock `AIProvider` and its currently selected model.
  A new model-selection pass happens only if the evaluation planned in `plan.md` shows that the
  model is not viable for this prompt.
- Analysis covers one request at a time. Bulk analysis of every failure in a run is out of scope,
  consistent with the project's caution about multi-request AI work on local CPU inference
  (AP-011 through AP-015).
- The confidence threshold for "insufficient evidence" (FR-008) is set and justified in
  `plan.md`.
- The guided workflow's `ApiModel`, `TestModel` and dependency data remain in memory only. This
  feature does not persist them. It stores only the context it used, inside each analysis.
- AP-017's API-only run endpoints are not supported. Adding them later would reuse the same
  analysis core.
- This feature extends AP-025's stored data with one new record kind and follows AP-025's rules:
  storage initializes automatically, corrupted storage fails explicitly, and tests are isolated
  from a real instance's storage.
