# Quickstart: Validating AI Failure Analysis (AP-031)

This guide proves the feature works from end to end. Request and response shapes are in
[contracts/failure-analysis-api.md](./contracts/failure-analysis-api.md), and types are in
[data-model.md](./data-model.md). This guide does not repeat them.

## Prerequisites

- Node.js 20 and `npm install` at the repository root.
- The automated scenarios need no model. Tests run with `AI_PROVIDER_MODE=mock` plus scripted
  providers (research D11).
- The manual scenarios need `AI_PROVIDER_MODE=local` and a cached local model
  (`AI_MODEL_ID`, default `onnx-community/Qwen2.5-0.5B-Instruct`). The first load may download the
  model into `AI_MODEL_CACHE_DIR`.
- Use a throwaway database for the manual runs: `APIPILOT_DB_PATH=./.tmp/ap031.db`.

## Automated validation

```bash
npm test          # all workspaces; includes the new unit and integration suites
npm run lint
npm run build
```

Expected: everything passes. The new suites cover:
- *(amended 2026-09-24)* the classification rules: every rule's match and non-match cases, rule
  precedence, the linear service-name scan, and the whole evaluation corpus classified exactly as
  labelled (SC-006, research D15);
- *(amended 2026-09-24)* the v4 explanation validation, including the contradiction check, and
  the `kept-previous` replacement rule (research D16, D18);
- *(amended 2026-09-24)* startup removal of legacy analyses (research D19);
- evidence extraction and ordering;
- redaction of headers, URL, JSON and non-JSON bodies, and the output scan (SC-003);
- the parse, validation and conclusion rules, including all three insufficient-evidence reasons;
- viability refusal;
- specification-context matching, with all four unavailable reasons and the upstream outcomes;
- the repository upsert and eviction;
- every route check in the contract table;
- the in-flight 409;
- the frontend panel states.

Opt-in real-model evaluation (research D11), which is never part of `npm test`:

```bash
npm run test:ai-real:failure-analysis -w backend
```

Expected *(amended 2026-09-24, research D20)*: the test prints, for the fixture corpus:
- the usable-explanation rate: structured, citing valid evidence, and not contradicting the
  rule-decided cause;
- the contradiction rate;
- latency.

Record the figures in `specs/030-ai-failure-analysis/evaluation.md`. SC-006 needs a usable rate of
at least 80% and a contradiction rate of at most 10%. Run it with the default model and with
`AI_MODEL_ID=onnx-community/Qwen3-1.7B-ONNX`. A default-model change goes through AP-004, with the
user's approval.

## Manual scenarios

Start the app with `npm run dev`, using `AI_PROVIDER_MODE=local`.

### 1. A collection ApiPilot did not generate (User Story 1, User Story 2 scenario 3)

1. On the **Import & Run Collection** page, upload a small collection with the `local` tier. It should contain
   one request to a closed port (for example `http://localhost:9/`) and one request whose
   `pm.test` expects status 201 from an endpoint that returns 404.
2. Run it. Both requests fail.
3. Choose **Analyze failure** on the connectivity failure. Expected:
   - the panel shows "Waiting for the local AI", then "Generating", each with an elapsed timer;
   - *(amended 2026-09-24)* the cause "Potential environment issue" with a rule badge, the
     strength "High" (no number), and the rule "No response was received";
   - the evidence that decided it in deterministic wording, with a collapsed "Other evidence
     considered" section;
   - a summary and investigation steps with the AI badge and the "AI inference, not a confirmed
     root cause" label, and "Specification context unavailable: not generated by the current
     workflow".
4. Analyze the 404 failure. Expected:
   - the evidence includes the failed test name and message, the request line, and the redacted
     body excerpts;
   - an `Authorization` header you added shows `[redacted]`.

### 2. A generated collection with a workflow (User Story 2)

1. Complete the guided workflow for a specification with a CONFIRMED create → get workflow.
   Approve the workflow and hand off to **Import & Run Collection**.
2. Point `baseUrl` at a target where the create step fails, then run the collection.
3. Analyze the failed get step. Expected: specification context shows the operation path and
   method, the scenario, the documented status codes, and the upstream create step with the
   outcome `failed`.
4. Edit the get request in the collection editor, run again, and analyze. Expected: the context
   notes that the request was edited after generation.
5. Start a new guided workflow in the same session, then analyze a failure from the earlier run.
   Expected: context unavailable, reason "not generated by the current workflow". The analysis
   stored in step 3 still shows its original context.

### 3. Persistence and replacement (FR-013, FR-014, FR-015)

1. Stop and restart the backend with the same `APIPILOT_DB_PATH`, then reopen the earlier run from
   the run history. Expected: the analyses stored earlier are shown unchanged.
2. Analyze an already-analyzed failure again. Expected: the new analysis replaces the old one.
3. Set `AI_INFERENCE_TIMEOUT_MS=1000` and restart, then analyze again. *(Amended 2026-09-24)*
   Expected: a `kept-previous` outcome. The earlier stored analysis is still shown, with a
   plain-language note that the new explanation is unavailable, for example because it timed out.
4. *(Added 2026-09-24)* Restart with `AI_PROVIDER_MODE=mock`, whose placeholder output is never a
   valid explanation (research D11), and analyze a failure that has no stored analysis. Expected:
   the rule-decided cause, its strength and the evidence are shown and stored, with "AI
   explanation unavailable" and the reason in place of the summary and steps (FR-006). This runs
   fully offline.

### 4. Guards (FR-002, FR-016)

- Use the API directly (see the contract) to request analysis of a passed result. Expected: 409
  `result_not_failed`.
- Start an analysis, then start another for a different failed result in the same session.
  Expected: 409 `failure_analysis_in_progress` naming the first result. In the UI, every
  "Analyze failure" action stays disabled until the first finishes, including after a page reload.
- Start an analysis while a run is still executing, on a failure it has already recorded.
  Expected: the analysis proceeds normally.
- Start an AI scenario enhancement in another browser session, then analyze a failure. Expected:
  "Waiting for the local AI" with an elapsed timer, then "Generating".

### 5. Privacy spot-check (SC-003)

With a `local`-tier run whose request carries a bearer token and a JSON body containing
`"password"`, analyze the failure. Then check the backend log output and the analysis JSON
returned by the GET list route. Expected: no token or password value appears in either.
