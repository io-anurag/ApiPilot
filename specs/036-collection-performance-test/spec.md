# Feature Specification: Performance Test from a Postman Collection

**Feature Branch**: `[036-collection-performance-test]`

**Created**: 2026-10-02

**Status**: Draft

**Input**: User description: "I created a workflow, check the image, this has all variables set, how
to extract & set token for subsequent requests & use of variables like {{$randomName}}. Now I want to
use this flow in my performance tests." Followed by: "So you mean I need to define all the steps once
again for K6 run" and "lets do a new spec" (2026-10-02, about a stored collection whose eight
requests, `POST /auth/token` then customer create, read, update and delete, then `/health` and
`/version`, pass in Import & Run Collection).

**Product identifier**: `AP-036` (post-MVP). This spec directory is numbered `036` per the
repository's sequential feature-directory convention; the directory number and the `AP-###`
identifier happen to coincide here but remain independent. `AP-036` is the canonical identifier
used in cross-references, commit messages, and `specs/ROADMAP.md`.

**Relationship to prerequisite specifications**: This feature builds a performance plan from a
Postman collection stored in Import & Run Collection, so that a flow that already passes as a
functional run can be load-tested without defining its steps again. It is a third source of
performance plans, beside the guided workflow's Performance Testing stage (AP-029,
`specs/031-k6-performance-testing`) and the quick performance test (AP-032,
`specs/032-quick-performance-test`). It reuses, unchanged:
- stored collections, their environment, variable overrides, edits, folder and collection auth,
  and the per-run selection and order (AP-026 and AP-028, `specs/026-external-collection-execution`,
  `specs/028-collection-editor-ui`);
- the plan's expected statuses, removal and restore, order, think time, load profiles, thresholds,
  target environments, script generation and download, run trigger, live progress, cancel,
  persistence of runs and reports, Run again and Restore (AP-029);
- the write-operation summary and its markers, counted per step (AP-032 FR-009 to FR-012, as
  amended by AP-035 FR-023);
- captures and bindings: a capture is attempted only on an expected status, succeeds only for a
  string, number or boolean, and a failed capture cuts the rest of the journey short; captured
  values are never stored, shown, logged or reported (AP-035, `specs/035-user-defined-journeys`,
  FR-010, FR-019, FR-020, FR-033);
- the script check that user-supplied scripts pass (AP-034, `specs/034-run-user-k6-script`).

It does not change how Import & Run Collection runs a collection. The collection's scripts still
run there exactly as authored. It does not change the guided or quick plans, which can exist beside
a collection plan.

It differs from the existing plans in three ways, each stated as a requirement below:
- The steps come from a collection, not from an OpenAPI specification. Without a specification, a
  step's expected statuses come from the collection's own status assertions or from the engineer,
  never from a guess (FR-011, FR-012).
- The collection's scripts are never run during conversion. A fixed set of statement forms is
  recognised and converted into captures and expected statuses. Everything else is listed, never
  guessed and never silently dropped (FR-005 to FR-010).
- A request whose values only feed authentication runs once before the load, not in the measured
  journey (FR-027 to FR-029).

**Governance**: The script is generated by ApiPilot, but from requests authored outside it.
Constitution XVII's 2026-09-24 exception covers a script generated from a plan built from an
approved TestModel (AP-029) or an uploaded specification (AP-032). It does not name a plan built from
an uploaded collection. This feature is a performance plan (Clarifications, 2026-10-02), so it
**requires a constitution amendment** that extends the 2026-09-24 exception to AP-036 plans. That
amendment is constitution v2.7.0 (2026-10-02), and it MUST be merged before implementation starts.
It rests on the conditions below. What AP-036 lacks, compared with AP-032, is that ApiPilot did not derive the
requests. It replaces that with a conversion review that makes every request, captured value and
unconverted statement visible before the run, as AP-032 makes every write visible. The conditions:
- the collection's scripts are never run by the conversion, and nothing in them reaches the script
  as code. Request content and recognised field paths and header names are written only as data
  (FR-005, FR-023);
- no secret value is written into the script: variables and secret literals reach it only as
  environment references (XVIII; FR-014, FR-015);
- the engineer reviews the conversion, including every request left out and every statement not
  converted, before a script can be generated (XI, XIX; FR-018);
- every step records the collection request it came from, and every capture records the script line
  it came from (XIII; FR-024).

Constitution XV is respected because a binding is created only from a value the collection's own
script sets, by the name the collection's own requests use. ApiPilot infers no relationship between
requests. The plan's Constitution Check records the v2.7.0 amendment as a blocking prerequisite
for `/speckit-implement` until it is merged.

## Clarifications

### Session 2026-10-02

- Q: Should the converted test be a performance plan, which needs a constitution XVII amendment, or a
  k6 script handed to Run k6 Script under the existing exception for user-supplied scripts? → A: A
  performance plan, with the plan's per-step features. The XVII amendment is drafted as part of this
  feature (Governance).
- Q: How often does a credential request (one whose values only feed authentication) run under
  load? → A: Once before the load starts. Its values are shared by every virtual user, and each
  virtual user refreshes them before they expire when the response states a lifetime, as AP-029
  FR-009 and FR-015 do (FR-027).
- Q: When a collection sets a variable with `pm.collectionVariables.set` or `pm.globals.set` and a
  later request uses it, does the load test use the captured value even where Postman would prefer an
  environment value of the same name? → A: Yes. It always binds to the captured value, whatever its
  scope. The review notes each such capture (FR-008, Edge Cases).
- Q: Should a literal value in a custom header whose name suggests a credential, such as
  `X-API-Key`, be kept out of the script like an auth-field literal? → A: Yes. A header whose name
  contains `key`, `token`, `secret`, `password`, `auth` or `session`, ignoring case, is a credential
  header. Its literal becomes a secret environment value, and the review lists it with the matching
  rule (FR-014, FR-015).
- Q: Should values generated for `{{$randomEmail}}`, `{{$guid}}` and similar change from one run to
  the next? → A: Yes, for the unique ones (`$guid`, `$randomUUID`, `$randomEmail`,
  `$randomUserName`). A run tag is passed to k6 as a run setting when a run starts from ApiPilot, so
  the script stays byte-identical. A copy run without the tag falls back. AP-029's unique fields are
  unchanged (FR-013, Edge Cases).
- Q: Must a collection have passed Import & Run's one-time "not generated or verified by ApiPilot"
  confirmation before a performance plan can be built from it? → A: No. The conversion review is the
  gate, and it carries the same statement (FR-018).

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Load-test a collection flow without defining its steps again (Priority: P1)

A performance engineer has a stored collection whose run passes: `POST /auth/token`, then `GET`,
`POST`, `GET`, `PATCH` and `DELETE` on `/api/v1/customers`, then `GET /health` and `GET /version`.
The token request's test script sets `access_token` from the response body, and the collection's
auth is a bearer token `{{access_token}}`. The `POST /api/v1/customers` test sets `customer_id` from
the body field `id`, and the next three requests use `{{customer_id}}` in their path.

In the collection's run panel the engineer chooses **Set up a performance test**. ApiPilot builds a
plan whose steps are the selected requests in the run order the panel shows. Each step is named after
its folder and request. ApiPilot shows that `access_token` is captured by the token request and sent
as the bearer token of every later step. It also shows that `customer_id` is captured by the POST and
used in the path of the GET, PATCH and DELETE that follow, so neither is a value the environment must
provide. The expected statuses come from each request's `pm.test` status assertions.

Because `access_token` only feeds authentication, the token request is shown as "run once before the
load", not as a journey step. The engineer reviews the conversion, chooses an environment, a smoke
profile, generates the script and starts the run. The token is obtained once and shared. On every
iteration, each virtual user creates, reads, updates and deletes its own customer. The report names each step after its collection request and shows each capture's
successes and failures.

**Why this priority**: It is the request itself: the steps, order, token and id already exist in
the collection, and today the only way to load-test them is to define the steps again.

**Independent Test**: Against a local test server that issues a token, creates customers with new
ids and answers 401 without a token and 404 for an unknown id, upload a collection and environment
like the one above. Build the plan from it, review it, generate the script and run a smoke test with
two virtual users. Check that no step needed `access_token` or `customer_id` from the environment,
that every customer request carried a token the server issued, that every GET, PATCH and DELETE used
the id from the POST of the same virtual user and iteration, and that no 401 or 404 was received.

**Acceptance Scenarios**:

1. **Given** a stored collection, **When** the engineer chooses **Set up a performance test**,
   **Then** a plan is built whose steps are the selected requests, in the run-order list's order,
   each named by its folder path and request name.
2. **Given** a test script that runs `pm.environment.set("access_token", pm.response.json().access_token)`,
   **When** the plan is built, **Then** that step has a capture `access_token` from the body field
   `access_token`, and the capture names the script and line it came from.
3. **Given** a later request whose auth, inherited from the collection, is a bearer token
   `{{access_token}}`, **When** the plan is built, **Then** that step's token is bound to the
   capture, and `access_token` is not listed as an environment value for it.
4. **Given** `const body = pm.response.json(); pm.collectionVariables.set("customer_id", body.id);`,
   **When** the plan is built, **Then** the step has a capture `customer_id` from `id`, and every
   later `{{customer_id}}` is bound to it.
5. **Given** `pm.test("created", () => pm.response.to.have.status(201))`, **When** the plan is
   built, **Then** the step's expected status is 201, labelled "from the collection's test".
6. **Given** a built plan, **When** the engineer has not reviewed the conversion, **Then** the
   script cannot be generated, and the plan says what remains to review.
7. **Given** the token request, whose only capture feeds later steps' auth, **When** a run with two
   virtual users and five iterations ends, **Then** the token request was sent once before the load
   (plus any refreshes), and the report counts it apart from the journey's steps.
8. **Given** a token response carrying `expires_in` shorter than the run, **When** the run passes
   that lifetime, **Then** each virtual user has obtained a new token through the same request before
   expiry, and the report shows the refreshes.

### User Story 2 - Generated values from Postman's dynamic variables (Priority: P2)

The collection's `POST /api/v1/customers` body is
`{ "name": "{{$randomFullName}}", "email": "{{$randomEmail}}" }`. In Postman each run sends new
values. Under load the engineer needs every virtual user and iteration to send its own values,
otherwise creates collide.

When the plan is built, ApiPilot shows that the step's `name` and `email` are generated when the
test runs, not values the environment provides. Each email is unique for each virtual user,
iteration and occurrence within a run.

**Why this priority**: Collections that create records rely on these variables. Without them, a
plan built from such a collection fails on its first conflicting create.

**Independent Test**: Build a plan from a collection whose POST body uses `{{$randomFullName}}`,
`{{$randomEmail}}` and `{{$guid}}`. Run a smoke test with three virtual users against a test server
that records each body and refuses a repeated email with 409. Check that no 409 was received, that
every name is a non-empty name, and that generating the script twice from the same plan gives the
same bytes.

**Acceptance Scenarios**:

1. **Given** a request using a supported dynamic variable, **When** the plan is built, **Then** the
   step's request preview shows it as "generated at run time" and it is not listed as an
   environment value.
2. **Given** a dynamic variable used twice in one request, **When** the request is sent, **Then**
   each occurrence gets its own value, as in Postman.
3. **Given** a request using a dynamic variable ApiPilot does not support, **When** the plan is
   built, **Then** the request is left out with the reason naming the variable, and the engineer can
   edit the request in the collection editor and rebuild.

### User Story 3 - See and fix what was not converted (Priority: P3)

A collection's scripts do more than set variables from a response: a collection pre-request script
logs in with `pm.sendRequest`, one test checks a response body field, and another sets a value only
when a condition holds. The engineer needs to know what the load test will and will not do before
running it.

The conversion review lists each statement that was not converted, with its request, script, line
and reason, and each request that was left out. A value set only by an unconverted statement becomes
an environment value, named as such. Where a value was not recognised, the engineer can add the
capture themselves on that step and bind it on later steps, as in a user-defined journey.

**Why this priority**: Faithfulness depends on it. Without the list, a plan could silently behave
differently from the functional run it came from.

**Independent Test**: Build a plan from a collection with a `pm.sendRequest` pre-request script, an
`if` around a variable set, a body assertion and an unsupported auth type. Check that each appears in
the review with its location and reason, that the request with unsupported auth is left out, that the
conditionally set variable is listed as an environment value, and that adding a capture by hand
removes it from that list.

**Acceptance Scenarios**:

1. **Given** a script statement outside the recognised forms, **When** the plan is built, **Then**
   it is listed with its request, whether it is a pre-request or test script, whether it belongs to
   the request, a folder or the collection, its line, and the reason.
2. **Given** a request that cannot be sent under load (unsupported auth type, file upload, unsupported
   dynamic variable), **When** the plan is built, **Then** it is listed as left out with the reason,
   and later steps that used a value it captured fall back to an environment value, named as such.
3. **Given** a step, **When** the engineer adds a capture by field path or header name, **Then** it
   behaves as an AP-035 capture, and the engineer can bind it on later steps. A typed field path is
   accepted with "Not documented in a specification".

### User Story 4 - An environment from the collection's values (Priority: P4)

The collection already has every variable set: its environment file, its defaults and the overrides
the engineer typed. The engineer does not want to type them again into a target environment.

From the plan, **New environment from this collection** creates a target environment with the values
the plan needs, as the collection would resolve them, and the collection's base URL variable as the
environment's base URL. The values are copied without being shown.

**Why this priority**: Useful, but the plan works with any target environment. Without this story the
engineer types the values once.

**Independent Test**: Build a plan from a collection whose environment sets `baseUrl`, `client_id`
and `client_secret`. Create an environment from it and check that the values checklist shows each as
**Present**, that the create response contains no value, and that editing a value in the collection
afterwards does not change the environment.

**Acceptance Scenarios**:

1. **Given** a plan built from a collection, **When** the engineer chooses **New environment from
   this collection** and names it, **Then** a target environment is created with the tier of the
   collection, the values the plan needs and the base URL.
2. **Given** the new environment, **When** its values are listed, **Then** each is shown as present
   or missing, never by value.

### Edge Cases

- **Variables before their capture.** A `{{name}}` used before any earlier step captures it is an
  environment value, as in Postman, where it resolves to the environment's value until a script sets
  it. A name captured again by a later step binds the references after it to the newer capture.
- **Scope precedence.** Postman resolves a name from the narrowest scope that holds it. A value set
  with `pm.globals.set` or `pm.collectionVariables.set`, while the environment also sets that name,
  is not what Postman sends next. The conversion binds the reference to the capture whatever its
  scope. For each such capture, the review notes that Postman would send the environment's value
  instead if the environment sets one (Clarifications 2026-10-02). *(Amended by plan, research R6: whether the environment sets a
  name depends on values, which change on every functional run.)*
- **Folder and collection scripts.** Postman runs a folder's or the collection's test script for every
  request inside it. A recognised capture in such a script is a capture on every step that inherits
  it, and each is listed.
- **Values that are not scalars.** A capture of an object or array, or of a missing, empty or `null`
  field, fails at run time and cuts the journey short (AP-035 FR-010).
- **A login that also returns an id.** A request whose captures feed both auth and anything else, such
  as a user id used in a path, is not a credential request (FR-027). It stays a journey step and runs
  on every iteration, and the review says why.
- **Several credential requests.** Each one is sent once before the load, in run order. A credential
  request whose own request uses a value captured by another one runs after it.
- **Captures from a non-expected status.** Postman sets a variable whatever the status. Under load, a
  capture is attempted only on an expected status (AP-035 FR-033). The review states this once.
- **`pm.setNextRequest`, `pm.execution.skipRequest` and `postman.setNextRequest`.** They change the
  run's order. They are not converted, and the review lists them. The plan's order is the run-order
  list's order.
- **Iteration data.** `pm.iterationData` and `{{name}}` from a data file are not available. The run
  panel has no data file, and such a name is an environment value.
- **Literal hosts.** A request whose URL holds a host rather than the base URL variable is sent to that
  host. Every such host is listed in the plan and at the run trigger.
- **Disabled items.** Disabled headers and query parameters are not sent, as in Postman. Requests
  unchecked in the run panel are not in the plan.
- **The collection changes.** An edit to the collection, or its deletion, marks the plan out of date
  with its collection (FR-022). Values a functional run saves back do not, because the plan uses no
  collection value. A new upload is a new collection. *(Amended by plan, research R13.)*
- **More steps than allowed.** A selection of more than 100 requests is refused with the count, and the
  engineer narrows the selection in the run panel.
- **Repeated runs.** Unique generated values carry the run's tag, so a second run from ApiPilot sends
  new emails, user names and UUIDs (FR-013). A downloaded copy run without the tag repeats the same
  values on every run. AP-029's unique email and UUID fields are unchanged, and still repeat across
  runs.
- **Nothing left.** When every selected request is left out, the plan says so and cannot generate a
  script.

## Requirements *(mandatory)*

### Functional Requirements

**Building the plan**

- **FR-001**: An engineer MUST be able to build a performance plan from any collection stored in
  Import & Run Collection, uploaded or handed off from the guided workflow, through **Set up a
  performance test** in that collection's run panel. It MUST NOT need an OpenAPI specification or a
  guided workflow, and MUST NOT read or change the guided or quick plans.
- **FR-002**: The plan's steps MUST be the requests selected in the run panel, in the run-order list's
  order at the time the plan is built (by default every request in the collection's order), folders
  flattened, as one journey. Each step MUST keep its request's identifier, folder path and name. A
  selection of more than 100 requests MUST be refused with the count.
- **FR-003**: Each step MUST send what the functional run sends for that request: method, URL, query
  parameters, headers and body, with its auth taken from the request or inherited from its folders or
  the collection as Postman does, with the engineer's saved edits applied, and with disabled items
  left out. Variables MUST be resolved only at run time (FR-008, FR-012, FR-014).
- **FR-004**: A request MUST be left out, with the reason, when its auth is not none, inherited,
  bearer, basic or API key (header or query), when its body is form-data, a file or GraphQL, or when
  it uses an unsupported dynamic variable (FR-013). *(Amended by plan, research R4: form-data is left
  out, because the script would need new runtime code to send multipart.)* Left-out requests MUST be listed in
  the plan's **Left out** view. None MUST be dropped silently.

**Converting scripts**

- **FR-005**: Building a plan MUST NOT run any of the collection's scripts, evaluate any expression in
  them, or send any request. Scripts MUST be read only as text, against the fixed set of forms in
  FR-006 and FR-011.
- **FR-006**: A statement in a test script MUST be converted into a capture on the steps it applies to
  when it sets a variable in any scope (`pm.environment`, `pm.collectionVariables`, `pm.globals`,
  `pm.variables`, or the legacy `postman.setEnvironmentVariable` and `postman.setGlobalVariable`) to
  either:
  - a field of the JSON response body (`pm.response.json()` or `JSON.parse(responseBody)`), read
    directly or through a local name assigned once from it, by property names and literal indices;
  - a response header read by its literal name.

  The exact accepted forms MUST be enumerated in the plan's research and covered by tests.
- **FR-007**: Only statements at the top level of a script, or directly inside the callback of a
  `pm.test`, MUST be recognised. A statement inside a condition, loop, function or `try`, one using a
  computed name or value, and any other statement MUST NOT be converted.
- **FR-008**: Each `{{name}}` in a later step's URL, query parameters, headers, body or auth fields
  MUST be bound to the latest capture of that name on an earlier step, whatever the capture's scope,
  with the scope note of Edge Cases (Clarifications 2026-10-02). A bound name MUST NOT be listed as an
  environment value for that step. Captures and bindings MUST follow AP-035's run-time rules, and
  moving or removing a step MUST respect AP-035's order checks.
- **FR-009**: Pre-request scripts MUST NOT be converted. Each non-empty pre-request script that applies
  to a step MUST be listed with its owner (request, folder or collection).
- **FR-010**: Every statement not converted, in a script that applies to a step, MUST be listed with
  the step, the script (pre-request or test), its owner, the line and the reason.

**Expected statuses**

- **FR-011**: A status-code assertion in the forms enumerated in the plan's research (at least
  `pm.response.to.have.status(n)`, an equality check of `pm.response.code` with a literal, and a
  `oneOf` check of it against literals) MUST set the step's expected statuses, labelled "from the
  collection's test". Other assertions MUST be listed as not converted.
- **FR-012**: A step with no recognised status assertion MUST start with no expected status and MUST
  block script generation until the engineer sets one (AP-029 FR-012a). ApiPilot MUST NOT pre-fill a
  status from the method or the request.

**Dynamic variables**

- **FR-013**: The dynamic variables in the plan's supported list MUST be generated in the script at
  run time, with each occurrence getting its own value. The list MUST include at least `$guid`,
  `$randomUUID`, `$timestamp`, `$isoTimestamp`, `$randomInt`, `$randomFirstName`, `$randomLastName`,
  `$randomFullName`, `$randomUserName`, `$randomEmail`, `$randomPhoneNumber`, `$randomAlphaNumeric`
  and `$randomBoolean`. `$guid`, `$randomUUID`, `$randomUserName` and `$randomEmail` MUST be unique for
  each virtual user, iteration and occurrence within a run, and MUST also carry a run tag that differs
  between runs started from ApiPilot. The tag reaches k6 as a run setting, not as part of the script,
  so the script stays byte-identical. A copy run without the tag generates the values without it
  (Clarifications 2026-10-02). Values MUST be derived from the run tag, the virtual user, the
  iteration and the occurrence, and from word lists written into the script. Other generated values
  do not use the tag. They MUST NOT come from a library outside the script. `$timestamp` and `$isoTimestamp` are the run's clock. Any
  other `{{$name}}` MUST leave its request out (FR-004).

**Values, secrets and environments**

- **FR-014**: Every other `{{name}}` MUST be a value of the target environment, under AP-029 FR-013
  and FR-014. A value MUST be marked secret when it fills an auth field or a **credential header**.
  A credential header is `Authorization`, `Proxy-Authorization`, `Cookie`, or any header whose name
  contains `key`, `token`, `secret`, `password`, `auth` or `session`, ignoring case (Clarifications
  2026-10-02). *(Amended by plan, research R12: the upload keeps no secret marking from the
  environment file.)*
- **FR-015**: A literal value in an auth field or in a credential header MUST NOT be written into the
  script. It MUST become a secret environment value, under a name ApiPilot gives it and lists. The
  review MUST list each such header with the rule that matched its name. Other literal values in a
  request MUST be written into the script as data, and the plan MUST say so.
- **FR-016**: When every step's URL starts with the same `{{name}}`, that name MUST be the
  environment's base URL. Every host written literally in a step's URL MUST be listed in the plan and
  at the run trigger.
- **FR-017**: **New environment from this collection** MUST create a target environment with a name
  the engineer gives, the collection's tier, the base URL and the values the plan needs, as the
  collection would resolve them (overrides, environment file, collection defaults), plus the literals
  of FR-015. Values MUST be copied on the server, and the copy action MUST NOT return any value. The
  new environment is then like every other target environment. The collection MUST NOT change, and
  later changes to it MUST NOT change the environment. *(Amended by plan, research R17.)*

**Review**

- **FR-018**: Before a script can be generated, the engineer MUST review the conversion. The review
  shows, per step, its source request, captures with their script lines, bindings, the source of its
  expected statuses, generated values and environment values. It also lists the left-out requests,
  the statements not converted, the pre-request scripts and the scope-precedence notes. The review
  MUST state that the requests and scripts were not generated or verified by ApiPilot. Rebuilding the
  plan MUST require a new review. Building a plan MUST NOT require AP-026's first-run confirmation of
  the collection; the review is the gate (Clarifications 2026-10-02).
- **FR-019**: The engineer MUST be able to add a capture to any step, and bind it on later steps, as
  in AP-035. A capture added this way MUST be labelled as set by the engineer, and a typed field path
  MUST be accepted with "Not documented in a specification".

**Reuse of the performance plan**

- **FR-020**: The plan MUST offer AP-029's and AP-032's controls: the write summary per step, removal
  and restore, expected statuses, step order, think time, load profile, thresholds, script generation
  and download with its environment template, the out-of-date marking, k6 readiness, the run trigger,
  live progress, cancel, the report, Run again and Restore. Step body and parameter edits (AP-033)
  MUST NOT be offered. The plan MUST point to the collection editor instead.
- **FR-021**: The run trigger MUST name the target environment by name, tier and base URL, and MUST
  repeat the hosts of FR-016 and the write requests.
- **FR-022**: When the collection's content changes (an edit in the collection editor) or the
  collection is deleted, the plan MUST be marked out of date with its collection. *(Amended by plan,
  research R13.)* Until it is
  rebuilt, a script MUST NOT be generated or run. Rebuilding MUST keep the load profile, thresholds,
  think time, and the expected statuses and captures the engineer set for steps whose request still
  exists. It MUST name each step it could not keep them for. A deleted collection's plan cannot be
  rebuilt, and its runs and reports MUST be kept.
- **FR-023**: The same collection content, selection, order and plan choices MUST produce a
  byte-identical script. The script MUST contain no variable value and no literal of FR-015, MUST
  write collection content only as data, MUST pass AP-034's script check, and MUST name each request
  after its step, so that a downloaded copy run in Run k6 Script groups by step.
- **FR-024**: The run's snapshot and report MUST state that the plan came from the named collection,
  authored outside ApiPilot. They MUST name each step by its folder path and request name, show each
  binding's capture, step and script line or "set by you", and count each capture's successes and
  failures. They MUST contain no captured or environment value and no request or response content.
- **FR-025**: A session MUST hold at most one collection plan, in memory, beside the guided and quick
  plans. Building a plan from another collection MUST replace it after the engineer confirms. Runs
  MUST share the one-run-at-a-time slot. The collection plan's run list MUST show its own runs only.
- **FR-026**: No AI MUST take part in building, converting, generating, running or reporting. Scripts,
  collection values and the generated script MUST NOT be logged.

**Credential requests**

- **FR-027**: A step is a credential request when it has at least one capture, and every capture is
  used only in auth fields, or in an `Authorization` header, of later steps. A credential request MUST
  be sent once before the load starts, not as a journey step. Its captured values MUST be shared by
  every virtual user (AP-029 FR-009). The plan MUST show it apart from the journey, as "run once before
  the load", naming the values it provides and the steps that use them.
- **FR-028**: When the credential request's response carries an `expires_in` body field (the OAuth
  2.0 token-response lifetime, as AP-029 reads it), each virtual user MUST send the same request again
  before its values expire and use the new values. Virtual users MUST NOT all refresh at the same
  moment. Without a stated lifetime, nothing MUST be refreshed. Refreshes, failed refreshes, and
  authentication failures after an unrefreshed expiry MUST be reported as AP-029 FR-015 states.
- **FR-029**: Credential requests and their refreshes MUST NOT be counted in any journey step's
  requests or latency. The report MUST count them separately. When the credential request before the
  load does not receive an expected status, or a capture from it fails, the run MUST follow AP-029's
  behaviour for a token that cannot be acquired, and the report MUST name the request and the
  capture.

### Key Entities

- **Collection performance plan**: a performance plan whose source is a stored collection, named by
  its collection, the run order and selection it was built from, and the collection's content at
  that time. It has one journey and the plan settings of AP-029.
- **Collection step**: a step built from one collection request, keeping its request identifier,
  folder path and name, its request with variables unresolved, its expected statuses and their
  source, its captures and bindings, and its generated values.
- **Converted capture**: a capture made from a script statement, with the variable's name and scope,
  the field path or header name, and the script, owner and line it came from. A capture the engineer
  adds has the same shape, labelled as set by the engineer.
- **Credential request**: a collection step whose captures only feed later steps' authentication. It
  is sent once before the load and refreshed per virtual user when its response states a lifetime.
- **Conversion finding**: an item the engineer must review: a left-out request, a statement not
  converted, a pre-request script, or a scope-precedence note. Each has its location and reason.
- **Generated value**: an occurrence of a supported dynamic variable in a step's request, with its
  kind and its position in the request.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: For the eight-request collection in User Story 1, an engineer goes from the passing
  collection run to a started smoke run without adding a step, capture or binding, and without typing
  `access_token` or `customer_id` anywhere.
- **SC-002**: In that run, 100% of customer requests use the token and the id that the same virtual
  user obtained in the same journey, and no request receives a status that the collection's own run
  did not.
- **SC-003**: For a test set of collections covering each recognised form and each unsupported
  construct, 100% of the converted forms become the expected capture or status. 100% of the
  unsupported constructs appear in the review with their location, and none is converted.
- **SC-004**: Building the same plan twice and generating its script gives byte-identical scripts.
  No generated script contains a variable value or a literal from an auth field.
- **SC-005**: A plan builds from a 100-request collection in under 5 seconds on the machine running
  the backend.
- **SC-006**: In a smoke run with 10 virtual users and 10 iterations, no two `$randomEmail` or `$guid`
  values are equal. A second identical run from ApiPilot sends none of the first run's
  `$randomEmail` or `$guid` values.

## Assumptions

- The engineer has already run the collection successfully in Import & Run Collection. The plan does
  not need that run, but a passing run is the realistic starting point.
- Recognising a fixed set of statement forms covers the common way collections pass values: a test
  script sets a variable from the response. Other scripts are listed, not run. The constitution does
  not allow running them in a generated load test, and k6 cannot run Postman's script sandbox.
- Under load, only statuses and captures are checked (AP-029). Body assertions in the collection's
  tests are not converted.
- Run order and selection live in the browser until a reload (AP-026 FR-019). The plan takes them as
  they are when it is built.
- The collection's delay between requests is not carried over. Think time starts at AP-029's default.
- 100 steps is a limit chosen for review and report scale. A larger flow is better split into several
  collections or selections.
- AP-029's unique email and UUID fields still repeat across runs. Giving them the run tag is a
  follow-up outside this feature (Clarifications 2026-10-02).
- The plan lives in memory like the quick plan, so a backend restart loses it, and Restore of a past
  run applies (FR-020).
- k6 1.0.0 or later is installed by the engineer, as for every performance path.
